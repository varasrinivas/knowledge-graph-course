Learning Objectives

By the end of this capstone you will be able to:

  • Extract a structural graph from a real Java codebase (624 to 9,000+ files) with tree-sitter-java — and read its provenance report critically.
  • Verify a graph against ground truth before trusting any number it produces — the step no benchmark reader ever does.
  • Serve a large graph to any MCP-aware agent with the parametrized M09 server (--graph).
  • Run a two-arm token benchmark and produce your own measured table — per-question multiples, reduction percentages, exploration burden.
  • Explain your numbers the way this course taught you: per-question vs session-level, ceiling case vs median, and why a smaller repo can show a bigger multiple.

Skill level: Intermediate → Advanced

The Brief: Flip the Floor

In Capstone 1 you built the full three-layer stack — structural graph, OKF bundle, enrichment hook, MCP server, freshness gate — over orderflow, a 15-file repo. Your measured improvement was a single-digit multiple, and the course told you that was the correct, expected result: orderflow sits far below the ~500-file threshold where graph tooling pays for itself.

That lesson only lands completely when you see the other side. This capstone flips the setup: you will graph Apache commons-lang (624 Java files) and Spring Framework (9,247 Java files — over 13 million tokens of source), then run a deterministic benchmark harness that measures, for real structural questions, what an exploring agent would pay versus what one graph query costs.

By the end you will hold a benchmark table with your name on it — the same shape of table that M04 and M05 taught you to read with suspicion. Producing one yourself, and then explaining its numbers honestly, is the graduation exercise of this course.

BEFORE: In a village of 15 houses, you don't need a map. You can knock on every door in ten minutes, so a cartographer's services feel like overhead — you pay for the map and save almost nothing.

PAIN: Now you're a courier in a city of 9,000 buildings. "Deliver to everyone named Chen" means walking every street and reading every mailbox — not once, but for every single delivery order. The cost of not having a map isn't linear; the bigger the city, the more brutal every lookup becomes.

MAPPING: orderflow was the village; Spring Framework is the city. The extraction cost (building the map) is paid once — ~2.5 minutes. Every structural question afterwards ("who calls registerBeanDefinition?") is a map lookup instead of a door-to-door walk past hundreds of files. This capstone measures exactly how much the walk costs.

Concept: The Two Arms of an Honest Measurement

Every benchmark comparing "agent with graph" to "agent without graph" is secretly a claim about what the without arm costs. Get that arm wrong and the multiple is fiction. So before you run anything, understand precisely what our harness charges each side.

BASELINE arm (simulated exploration). The harness greps the repo for the call-site pattern \bsymbol( — a word boundary, the name, an opening parenthesis. That's what a competent agent actually greps: not the bare name, which over-matches comments and longer identifiers. Then it charges the full size of every matched file, at roughly 4 bytes per tokenThe unit LLMs read and bill by; ~4 characters of English/code on average. A 24KB file ≈ 6,000 tokens of context. — because to confirm which hits are real call sites and who contains them, files enter the agent's context whole. Ops = files opened.

GRAPH arm (one tool call). The harness charges the byte size of the JSON answer returned by graph_callers(), plus a one-time ~700-token architectural orientation read (the GRAPH_SUMMARY.md pattern from M11) amortized across the question count. Ops = 1 tool call.

Notice what the baseline is not: it is not what a lazy agent spends. A lazy agent reads three of the 46 matching files, answers from those, and is wrong about the other 43 call sites. The baseline is the mechanical floor of a correct answer — the honest denominator. That asymmetry (the graph is complete by construction; exploration is complete only if you pay for every file) is the entire economic argument of this course, made concrete.

TWO_ARMS — the same question, both ways
Real numbers from the Spring run: 174 files matched registerBeanDefinition( — ~764K tokens to confirm them all — versus a ~46K-token graph answer. 16.4x for this one question.
🎯 Why It Matters

On the Spring run, answering just 8 structural questions by exploration means opening 4,535 files ≈ 15.2 million tokens. That is not a marketing projection — you will reproduce it on your machine in Phase 4, in about 15 seconds of harness time. The graph answers the same 8 questions for ≈451K tokens.

⚠️ Common Misconceptions (about benchmarks like the one you're about to produce)

"116x means my monthly bill drops 116x." — No. These are per-question multiples for pure structural lookups — the same class of number as okf-rs's published ~400x per query. Sessions also spend tokens on reasoning, editing, and non-structural reads that no graph can remove; replicated session-level savings run 6.8x–49x.

"The tool picked easy questions." — The harness auto-selects symbols by caller count (structural relevance: the most-called methods are what developers actually ask about) — never by grep expense. Selecting the most grep-expensive names would manufacture a ceiling case, which is exactly the benchmark sin M04 taught you to spot.

"Bigger repo always means bigger multiple." — Bigger repo means bigger exploration burden (files opened per question). The multiple also depends on how big the graph's answers are — you'll see commons-lang beat Spring on the multiple for exactly this reason, and explaining it is part of Phase 5.

Concept: When the Graph Should Refuse to Guess

Java breaks the bare-name resolution you used on Python in a specific way: overloading and interface convention mean the same method name is defined in many places. In orderflow, decode_jwt had one definition; in Spring, getName has hundreds.

The extractor keeps the three provenance tags you know from M01 — with one addition:

TagMeaningExample (commons-lang run)
EXTRACTEDCallee defined in the same file — unambiguous local resolution2,055 edges
INFERREDExactly one definition of that bare name in the whole corpus5,921 edges
AMBIGUOUS2–8 candidate definitions; every candidate emitted, honestly labeled32,333 edges
unresolvedMore than 8 definitions (AMBIG_CAP = 8): no edges emitted at all10,258 calls to 36 names dropped — append, toString, get…

Why drop rather than emit? A call to a name defined 150 times carries no structural signal — emitting 150 candidate edges per call site is quadratic noise wearing an honesty costume. The first version of this extractor did exactly that and produced 183,568 edges for a synthetic repo whose true structure had under 6,000; the cap brought it back to 5,960 without losing a single seeded ground-truth edge. Refusing to guess is the honest answer here. Real tools do better not by guessing harder but by escalating to type resolution — M03's LSP ladderM03's resolution ladder: heuristic bare-name matching → LSP-backed disambiguation (ask the language server via textDocument/definition) → accept AMBIGUOUS. Each rung costs more and resolves more., where a language server like Eclipse JDT resolves the receiver's static type.

🔎 What Just Happened?

You now know how to read the extractor's closing line — unresolved: 10,258 calls to 36 over-ambiguous names dropped — as a feature report, not an error. It tells you which questions this graph can answer deterministically and which ones need a smarter tool. Ask it about toString and it will decline; ask it about registerBeanDefinition and it answers in one call.

Concept: Reading Benchmarks Honestly — Now With Your Own

M04 gave you the skeptic's checklist for other people's benchmarks: vendor-reported vs replicated, ceiling vs median, corpus topology. Now apply it to the table you are about to produce. Three questions matter:

  1. What level is the number? Per-question structural lookups (this harness, okf-rs's ~400x/query) vs whole sessions (CodeGraph's task benchmarks: OkHttp 645 files → 13%, Django ~3,000 → 36%, VS Code ~10,000 → 78%; independent Graphify replications 6.8x–49x). Both are true; they measure different things.
  2. What does the baseline assume? Ours: complete confirmation of every call-site grep hit. Weaker baselines (agent samples a few files) produce smaller multiples and wrong answers; stronger claims usually hide a lazier baseline.
  3. What was selected, and by whom? Symbols here are chosen by caller count, deterministically, before any cost is known. If you let the selector see grep expense first, you can make the aggregate say almost anything — try it in Going Further and watch the number inflate.

🔧 Troubleshooting

Windows: Filename too long during the Spring clone → Spring's docs tree overflows the 260-char path limit. Clone with git -c core.longpaths=true AND into a short path like D:\tmp — a long parent directory re-breaks it even with longpaths on.

Verify Against Ground Truth

This is the step no benchmark reader ever does — and the reason your numbers will deserve more trust than the ones on Medium.

STEP 4

Exact check on the synthetic repo

What & why: gen_java_repo.py is seeded: it writes known_truth.json alongside the code, recording that the deliberate god node Registry.lookup has exactly 1,192 callers on the full synthetic. Count the graph's edges into lookup and compare.

python
import json
g = json.load(open("synth-graph.json")); truth = json.load(open("synth-java/known_truth.json"))
callers = [e for e in g["edges"] if e["target"].endswith(".lookup")]
print(len(callers), "found, expected", truth["lookup_callers"])  # 1192 found, expected 1192
✅ Checkpoint

1192 / 1192. The instrument measures what it claims to measure.

STEP 5

Spot check on the real repo

What & why: ground truth for commons-lang is the source itself. Pick one caller from graph_callers("capitalize"), open the named file at the named line, and confirm the call site with your own eyes. Two spot checks are enough — the point is the habit, not the coverage.

✅ Checkpoint

You verified real edges by hand. Every number in Phase 4 now rests on an instrument you tested, twice, two different ways.

What a Real Live Run Looks Like

Everything above is the mechanical benchmark — no model in the loop. We also ran the Phase 6 live experiment for you once, so you can see what actually happens: the same four questions (2 structural, 2 logic) asked via claude -p against this spring-framework snapshot, with and without the graph MCP server registered. Same model (Sonnet) on both arms; the only variable is the graph. The table shows medians of 3 independent fresh sessions per cell (24 sessions, ~$2.59 total) with min–max spread — the same run-N-times-report-medians methodology the CodeGraph benchmarks use, because single sessions turned out to vary by up to 2x on identical questions.

Both runs, in plain language. Imagine answering questions about a library of 9,000 books (this codebase). Question: "which books mention Professor Smith?" Two ways to answer: walk the shelves and read every book that might mention Smith (exploration), or look Smith up in a pre-built card catalog (the graph).

The mechanical run was a paper estimate, no assistant involved. Hard way: 174 books mention Smith; reading them cover-to-cover is 764,000 pages — the price of being certain you missed nothing. Index way: the card is 2 pages. On paper the catalog wins by miles — that's the 33.7x. Honest, but it assumes a reader who reads entire books.

The live run hired a real assistant, and three assumptions broke. First, the real assistant has a photocopier that returns just the sentences mentioning Smith — it never reads whole books, so the "hard way" was cheap all along. Second, our homemade catalog is sloppy: the "Smith" card lists every Smith it ever saw, including 40 wrong ones — the card wasn't 2 pages, it was 40. Third, the assistant didn't fully trust our catalog and pulled a few books to double-check — paying for both methods. And on the "why did Smith's experiment fail?" questions, no catalog helps: you have to read and think either way.

Both measurements are right — they answer different questions. The paper estimate tells you the worst-case reading an index can spare you. The live run tells you whether this catalog saves this assistant money on these questions (here: no). A professionally-made catalog — compact cards, only the right Smiths — could still win. The only number that should drive a buying decision is the one you measure in your own library.

The graph arm lost — and repetition strengthened the verdict. Answer quality was comparable and correct on both arms — both found isBeanDefinitionOverridable at the same line, both traced the three-phase re-query in PostProcessorRegistrationDelegate. But at the medians the graph cost 71% MORE tokens (+119% on structural questions, +38% on logic). A first single-session run had shown +68% overall but a near-tie on the last logic question; across three sessions that "wash" did not survive — one lucky cheap session is exactly the kind of noise medians exist to remove. After a page of 33.7x mechanical multiples, this deserves an explanation, not a shrug:

  1. The live baseline never pays the whole-file floor. The mechanical benchmark charges the full size of every matched file, because that is the cost of certain confirmation. But a real agent's Grep returns matching lines, not whole files — the baseline answered the callers question in 4 turns mostly from grep output alone. Good line-granular search undercuts the worst case dramatically.
  2. This course's teaching-grade server sends bloated answers. Bare-name resolution fans registerBeanDefinition out to a huge caller list, AMBIGUOUS candidates included — one MCP answer was ~11K tokens. Production tools win partly because type resolution keeps answers small.
  3. The model didn't trust the graph blindly. On the forClass question it spent 9 turns cross-verifying graph claims against files — paying for both retrieval paths.
  4. Logic questions penalize the graph least — but it is still a penalty. At medians, logic questions cost +38% with the graph vs +119% for structural ones: reasoning dominates logic answers and no graph removes reasoning tokens, so the graph's overhead (schemas, bloated answers, verification) is diluted — not eliminated. One single session had shown a +2% near-tie; the spread across sessions (114K–228K on the same question) shows why one run proves nothing.
🎓 The Three Quantities

You now have three numbers for the same repo, and all three are correct — they just measure different things. The mechanical per-question floor (33.7x) measures worst-case exploration vs answer size, no model involved. The replicated session ranges (6.8x–49x) measure other people's stacks on other people's tasks. The live run on this stack (0.6x — a loss) measures a naive bare-name server against an agent with line-granular grep. Only the third describes your setup — which is why this capstone makes you run it. With a type-resolved graph, compact answers, and a long session amortizing the MCP schema overhead, the sign can flip back; proving that is the stretch experiment.
